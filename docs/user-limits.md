# 用户周期限额与安全回退

用户周期限额是独立的、显式启用的后台策略。没有策略或策略关闭时，请求仍使用原有鉴权、选路和扣费路径；它不重命名日卡字段，也不替换已有访问套餐。

## 计算口径

每个普通用户可配置三个同时生效的窗口：首次启用时间为锚点的固定五小时段、指定 IANA 时区的自然周（周一开始）和自然月。不是“最近五小时”的滑动窗口。首次有用量后，不能通过更换时区或锚点绕过已用额度。关闭再开启不会清空计数。

每个窗口独立设置金额与受理次数，零表示该项不限额。次数统计已受理的请求；之后失败、取消仍占受理次数，并单独计入失败数。同步请求的渠道重试不重复受理；批量任务按条目计数。模型范围沿用本项目已有的模型匹配规则，不改写转发模型 ID。

金额使用既有实际计费结果。已知价格的异步任务在受理时按其原有预扣金额占用；未知最终成本的同步请求先占用一笔小额预留，再按实际结果结算。**金额限制是受理门槛，不是已在途请求最终账单的硬上限。** 多个已受理请求仍可能使最终金额超过限额。结算不得为了把数字压到限额而少扣或重复扣费。

开启周期策略的普通用户暂不开放无法按该路径结算的实时会话；在升级连接前明确返回错误。管理员不受普通用户策略限制。用户界面只展示后台给出的窗口、用量、预留和待结算条数，不在浏览器重算周期或补账。

## 增量接口

- `GET /api/v1/user-limits/current`：登录用户自己的策略和用量。
- `GET /api/v1/user-limits/:id`：管理员读取指定用户。
- `PUT /api/v1/user-limits/:id`：管理员保存策略，携带读取时的 `revision`。修订冲突返回 409，重新读取后再决定修改，不覆盖他人的编辑。

这些是新增接口；既有业务端点的请求/响应结构保持不变。受理回执的标识由服务器产生，客户端不能指定另一用户的回执或补发结算。

## 数据迁移

实际执行入口是 `internal/db/db.go` 的 `InitDB` / `AutoMigrate`，新增 `user_quota_policies`、`user_quota_windows`、`user_quota_receipts` 三张表。模型定义在 `internal/model/user_quota.go`。没有基于历史日志猜测消费量的回填，也不改写旧 `users.monthly_*` 或访问套餐列。

窗口与回执保存受理当时的周期。跨周/月的迟到结算或退款仍归属于原窗口。异步任务的终态、回执、额度及原扣退费在同一数据库事务中提交；重复相同结算不再重复扣费，不同结果的重复结算明确报错。

启动迁移失败时应解决问题并重新启动同一版本，不能把缺表当作“没有限额策略”。数据库升级前照常做一致性备份。SQLite 的隔离回归不能代替每种生产数据库、每种部署拓扑的现场验收。

## 回退顺序

1. 通过部署现有的维护方式停止新的生成受理，保存策略状态并做一致性备份。
2. 保持新版本运行到已配置策略的请求和异步任务结算完成。关闭策略只停止新受理检查，已有回执仍按原路径结算。
3. 检查 `pending_receipts`。进程中断或数据库写入失败后，待结算不等于零费用。必须由后台依据实际任务、结果和账务证据核对；不能静默删除预留，也不能另走旧路径重复扣款。
4. 确认待结算工作已完成或逐项留证后再回退程序镜像，保留新增三表。不要用旧 users 表覆盖新余额，不要清空周期计数。

没有自动 DROP/DOWN 迁移。紧急提前回退时保留数据并记录未结工作；恢复限额前先完成后台核对。上述是运维说明，不会在前台自动执行，也不代表发布镜像已替代生产部署。
